# extDB3 reference comparison

The harness loaded the installed Windows extDB3 1.031 binary with its adjacent test allocator. The saved reference replay and the replacement replay share 16 identical call strings; all 16 responses match byte-for-byte, including SQL_CUSTOM formatting, the syntax-error and missing-call responses, log protocol calls, and lock behavior. Both async `slow` calls return `[1,[[0,"async"]]]`; polling returns `[3]` before the completed result. This reference capture was made against an earlier MySQL 8 test run, not MySQL 9.7.2.

The replacement completed a 10,255-byte SQL_CUSTOM result through both synchronous-overflow and async requests, using `4:` to detect multipart data and `5:` until the empty terminator. The archived reference's earlier large-value fixture returned `Error extDB3Exception Exception` for a `MYSQL_TYPE_LONG_BLOB`; it did not provide a comparable multipart result. The current `large` and `multiStep` fixtures differ from the archived SQL templates, so those cases are not byte-for-byte reference comparisons. Both fixtures passed against MySQL 9.7.2 on Windows and Linux.

I retried the reference binary against the isolated MySQL 9.7.2 server. `9:ADD_DATABASE:test` returned `[0,"Database Config Error"]`, so no SQL replay against MySQL 9.7.2 was possible with the reference. I also tried once with the server's global `require_secure_transport` temporarily off; the reference still failed. The setting was restored to `ON`. The replacement's test user independently requires SSL and authenticated successfully with `caching_sha2_password` over its verified TLS connection; an unrelated test CA was rejected on both Windows and Linux.

As a reference-only diagnostic, I temporarily changed the isolated `extdb_reference` account to MySQL 9.7.2's active `sha256_password` plugin; extDB3 then returned `[0,"Database Connection Error"]`. The account was restored to `caching_sha2_password`, and the server remains on `require_secure_transport=ON`. This did not make the reference client usable against MySQL 9.7.2.

The archived reference replay is evidence from the earlier MySQL 8 compatibility run, not a completed MySQL 9.7.2 differential suite. Direct reference parity for SQL errors and multipart output on MySQL 9.7.2 remains unverified. The Exile replay used actual SQL templates and source-derived call shapes but synthetic values; a runtime-captured call log remains unavailable.
